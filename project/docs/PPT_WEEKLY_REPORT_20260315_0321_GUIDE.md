**PPT 可直接使用文案（建议分两组，避免混淆）**

**（A）数据侧：坏视频导致训练“假死/极慢”**  
- 现象：训练中反复出现 `moov atom not found` 与 `Failed to open video file`（如 `meld_train_1166.mp4`）。  
- 影响：视频解码阶段耗时激增，epoch 进度长时间不前进，易误判为进程卡死。  
- 修复：执行 `check_media_health_dir.py` 定位坏样本；必要时归档/移走坏文件后复跑。  
- 工程收益：数据问题可定位、长时训练可恢复（tmux + checkpoint）。

**（B）续训侧：TensorBoard 曲线「断崖式」变化（本次重点）**  
- **现象**：首轮 run `VT_pretrain_3datasets_noDA_20260318_203248` 中断后，以 `--resume` 启动新 run `VT_pretrain_3datasets_noDA_20260319_232117`；在 TensorBoard 中对比两段曲线时，**损失等指标出现突变、不连续**（断崖），而非平滑衔接。  
- **根因（代码层面）**：`scripts/train.py` 在 `--resume` 时**只恢复了 model 与 optimizer**，**没有恢复学习率调度器 `scheduler` 的状态**（未执行 `scheduler.load_state_dict`）。优化器虽对齐 checkpoint，但 **lr 调度轨迹被重置**，导致同阶段训练动态与中断前不一致，曲线表现为断崖。  
- **解决策略**：① 代码：在 `pretrain` 模式的 resume 分支中，若 checkpoint 含 `scheduler_state_dict` 则一并恢复；② 实验：删除「scheduler 未修复时」产生的续训日志目录，从首次 run 的 checkpoint 用修复后代码续训，保证曲线可解释、可对比（操作见 **第七章**）。  
- **汇报口径**：断崖主要来自 **续训实现疏漏（scheduler 未恢复）**，而非数据集或模型权重随机跳变；修复后应观察到 **lr 与 loss 趋势可衔接**。

## 四、TensorBoard 断点续训曲线「断崖式」变化（专项复盘）

> **用途**：向听众解释「为何 checkpoint 恢复后 TensorBoard 上 loss 会突变」；与 **第三章第 6 页（B）组** 配套使用。根因来自项目内 `train.py` 实现，**置信度：高**。

### 4.1 现象

- 同一 VT 无 DA 实验在 **中断前后** 产生两个日志 run（如 `…20260318_203248` 与 `…20260319_232117`），在 TensorBoard 中并列查看时，**训练损失等曲线在衔接处出现阶跃、突变**，视觉上像「断崖」。  
- 与「训练慢」不同：断崖问题指向 **指标曲线不连续**；慢问题指向 **单 epoch 耗时过长**。

### 4.2 根因说明

**直接原因**：`scripts/train.py` 在处理 `--resume` 时，**仅恢复了模型权重与优化器状态**；在修复前，**未恢复学习率调度器 `scheduler` 的 `scheduler_state_dict`**。

| 恢复项 | resume 时（修复前） | 后果 |
|--------|---------------------|------|
| `model` | 已恢复 | 权重与 checkpoint 一致 |
| `optimizer` | pretrain 模式下已恢复 | 动量等状态一致 |
| **`scheduler`** | **未恢复** | **调度器内部步数 / 当前 lr 规划与真实 epoch 不一致**，等价于「从某 epoch 权重接着跑，但 lr 曲线从头再来」 |

**原理简述**：Cosine / Step 等调度器内部维护 **当前 step 与已规划的 lr 序列**。不恢复 scheduler 时，**学习率水平与变化节奏**与「已训练到的 epoch」不匹配，前向 loss 尺度随之突变，TensorBoard 上即表现为 **断崖**。

### 4.3 解决策略（工程）

1. **代码修复（已完成）**：在 `pretrain` 的 `--resume` 分支中，若 checkpoint 中存在且非空的 `scheduler_state_dict`，则调用 `scheduler.load_state_dict(...)`，与 model、optimizer **三者同步恢复**。  
2. **实验与日志策略**：若已在「未修复代码」下产生一段不可比曲线，可 **终止续训**、**删除该次 run 日志目录**，从 **首次 run 保存的 checkpoint** 用修复后脚本重新 `--resume`，获得 **单条可解释曲线**（或至少 lr 连续）。  
3. **验证建议**：续训后对比 **首 epoch 打印的 lr** 是否与预期调度一致；必要时在 `train.py` 每 epoch 记录当前 lr（便于周报举证）。

### 4.4 与坏视频问题的区分

| 维度 | 坏视频（moov / 打不开） | Scheduler 未恢复（断崖） |
|------|------------------------|---------------------------|
| 主要表现 | 极慢、长时间无新日志 | 有新日志，但 **loss 曲线衔接异常** |
| 归因 | 数据文件损坏 / 解码失败 | **训练脚本 resume 逻辑不完整** |
| 处理 | 健康检查、移走坏样本 | **恢复 scheduler + 规范续训流程** |
